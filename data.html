Data for researchers

The entire archive is open. Every model is asked the same fixed questions under fixed conditions (temperature 0, one shared system prompt, a completion cap of 2,000 max tokens, reasoning effort low), and each answer is stored with the model's release date, the date it was collected, and the exact capture settings used, so you can study how answers shift as models are released and updated over time. Free to use for research and journalism with attribution.

How to obtain the data

  • Programmatic (JSON). Start at /api/index.json, a catalog of every model and question with links to:
    /api/models/<slug>.json (one model, its full answer sheet) and /api/questions/<id>.json (one question, every model's answer).
  • Bulk / raw. The whole repository is public: github.com/kwartler/waiback.org. The data/ folder holds questions.csv, models.json, responses.json (every answer), prompts.json (the capture conditions over time), and the generated api/ files.
  • Reproducible. The capture and build scripts (build/generate.py, build/render.py) are in the same repo, so the full pipeline is inspectable.

What each record contains

Per-answer fields: question_id, answer, response_date (collected), prompt_tokens, completion_tokens, total_tokens, input_per_1m and output_per_1m (USD per million tokens, frozen at capture), cost_usd (computed from those), or_cost (OpenRouter's reported charge), temperature, prompt_sha (which system prompt was used), max_tokens (the completion cap actually used for that capture), reasoning_effort, and finish_reason. Per-model records add release_date, knowledge_cutoff, context_length, pricing, and description.

Retries and non-responses

Some models (usually reasoning or "thinking" models) return HTTP 200 but no visible answer: they spend the whole output budget on hidden reasoning. When that happens at the standard cap of 2,000 max tokens, the question is retried once at a larger cap of 5,000 max tokens. Two other cases also get one extra attempt (since 2026-11-22). The prompt, system prompt and temperature never change:

  • Cut off at the cap (the provider reports finish_reason: length): retried once at the larger cap. The fuller retry is shown, and the cut-off first attempt is kept in first_attempt, one click away on the page. Older answers that hit the cap carry a "cut off" or "likely cut off" badge instead.
  • Blocked by content moderation (finish_reason: content_filter): if the provider blocked the prompt (no output at all), there is no retry, because the same prompt is blocked again. If output was generated and then blocked, it is retried once at the same cap. The provider's own message is saved in refusal, error_message and native_finish_reason.

Every record therefore carries flags so you are never blind to a parameter change:

  • retry (bool): the answer was captured only after the larger-cap retry. Its max_tokens reflects the larger cap, and retry_reason states exactly what changed.
  • retry_success (bool, when retry is true): whether the retry produced an answer.
  • first_attempt / retry_attempt (object): the attempt that is not shown, with its own answer, tokens, cap and finish reason, so no call is ever discarded.
  • empty (bool): the model was reached but returned no content even after the retry. These non-responses are kept, not dropped, with retry_success: false and an explanatory retry_reason.
  • error (bool): the model could not be reached at all, so no answer was captured. This is distinct from a non-response: the provider rate-limited us (http 429), rejected the request (http 400/403), or no longer serves the model (http 404, delisted). error_status gives the short status and error_reason a plain-English explanation. These are re-attempted on later runs and clear automatically once a capture succeeds, so a rate-limited model can still fill in.

Browse both at Gaps, or get them all as JSON at /api/gaps.json, where each entry carries a kind of no_answer (reached but empty) or unavailable (could not be reached). The conditions block in every API file also reports max_tokens and retry_max_tokens.
